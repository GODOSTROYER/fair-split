# Security: secrets and the leak playbook

The repository stays private until the submission window and is then made public (ADR-0002), so every commit is
written as if public. Secrets live only in the gitignored `.env`, the Render services' own environment variables
(no environment group: `render.yaml` declares every name, never a secret value), GitHub environments
(`sandbox-smoke`, `eval-live`) and EAS secrets. Clients read only `VITE_PUBLIC_*` and `EXPO_PUBLIC_*`.

## Secrets on Render (render.yaml)

`tools/lib/blueprint.ts` checks this layout in CI (`tools/lint-render.ts`) and in `apps/tasks/test/render-blueprint.test.ts`.
The runbook for entering the values is `apps/tasks/README.md`, "Deploying".

| Name                            | Service         | Where the value comes from                                                                     |
| ------------------------------- | --------------- | ---------------------------------------------------------------------------------------------- |
| `FS_LINK_SIGNING_KEY`           | fs-api          | Prompted once (`sync: false`): 32 random bytes as 64 lowercase hex                             |
| `FS_LEDGER_SIGNING_KEY`         | fs-api          | Prompted once: 32 random bytes as 64 lowercase hex, different from the link key                |
| `FS_OPERATOR_PASSWORD_SCRYPT`   | fs-api          | Prompted once: `node tools/ops-hash-password.mjs` (the hash only; the password stays with you) |
| `JUDGE_CODE_SHA256`             | fs-api          | Prompted once, optional: the runbook's judge-code one-liner (the hash only)                    |
| `FS_KILL`                       | fs-api          | Prompted once, left blank: the deploy-wide kill override, not a secret                         |
| `FS_COOKIE_SECRET`              | fs-api          | Generated by Render (`generateValue`, a base64 256-bit value)                                  |
| `CRON_SECRET`                   | fs-api, fs-cron | Generated on fs-api; fs-cron reads it through `fromService`                                    |
| `FS_APP_DB_PASSWORD`            | fs-api          | Generated; migrate gives `fs_app` this password, the entry builds fs_app's URL from it         |
| `DATABASE_OWNER_URL`            | fs-api          | `fromDatabase`; only migrate uses it, the entry deletes it from `process.env` (ADR-0005)       |
| `PP_CLIENT_ID` … `PP_RECEIVERS` | fs-api          | Committed plain values: the simulator's fictional `fs-judge` app and accounts                  |

Render accepts a prompt left blank. So that a skipped prompt fails the deploy instead of deploying green, fs-api
refuses to boot on Render, naming the variable and never a value, without `FS_COOKIE_SECRET`,
`FS_LINK_SIGNING_KEY`, `FS_LEDGER_SIGNING_KEY` or `FS_OPERATOR_PASSWORD_SCRYPT` (`apps/api/src/env.ts`).
`JUDGE_CODE_SHA256` and `FS_KILL` may stay blank.

**The `PP_*` values are not secrets.** With `PP_MODE=simulator` they are copies of
`packages/paypal-sim/data/accounts.json`, fictional values on the reserved `example.org` domain that only the
in-process simulator accepts; they are not PayPal credentials, and the policy checks each against that file.
secretlint and `tools/guard-env.mjs` pass them. `.github/.gitleaks.toml` allowlists exactly the simulator apps'
client ids and secrets, and only in that file and `render.yaml` (both conditions must hold). A real sandbox app (`PP_MODE=sandbox`, untested) would be a secret:
its values must then be `sync: false` prompts, never committed (the policy requires it).

## Layers that stop a leak

| Layer                     | What it checks                                                                                               | Where                                             |
| ------------------------- | ------------------------------------------------------------------------------------------------------------ | ------------------------------------------------- |
| `.gitignore`              | `.env*` (except `.env.example`), keystores, credential JSONs, Firebase files                                 | Every commit                                      |
| `tools/guard-env.mjs`     | Any `.env` file; Anthropic, Google and PayPal secret patterns                                                | lefthook pre-commit; CI on changed files          |
| secretlint                | The recommended preset: staged files at pre-commit (via `tools/run-staged.mjs`), the whole tree in CI        | lefthook pre-commit; CI                           |
| gitleaks                  | Push: the pushed commits. PR: the PR's commits. Weekly and manual run: all history reachable from the ref    | `gitleaks.yml` (`gitleaks/gitleaks-action` v3)    |
| Fixture scrubber          | Tokens → `REDACTED`, emails → `sb-<hash>@sandbox.fairsplit.invalid`                                          | `@fairsplit/test-kit`; CI re-checks every fixture |
| `tools/scan-dist.ts`      | Secret env values present at build time and PayPal, Anthropic, Render and Google key shapes in `apps/*/dist` | The last step of fs-api's Render build            |
| `tools/assemble-media.ts` | `/media` serves only what `MEDIA_ALLOWLIST` names, never `media/` (prompts, labels, masters)                 | fs-api's Render build, before the dist scan       |
| GitHub push protection    | Known provider token formats                                                                                 | On push (enable in repo settings)                 |

`--no-verify` is forbidden. A hook that blocks a commit is fixed, never bypassed.

## GitHub settings before the first secret

- Environments `sandbox-smoke` and `eval-live`: Settings → Environments → the environment → Deployment branches
  and tags → Selected branches and tags → `main` only. A manual run can start any branch's copy of a workflow, so
  the smoke job also refuses every ref but `main` itself (`.github/workflows/sandbox-smoke.yml`).
- The ownership gate (`.github/workflows/ownership.yml`) runs on `pull_request_target` with `contents: read`. It
  checks out `main` and only reads the PR's commits with git. Never add a step there that installs, builds or runs
  the PR's code: that code would run with the base repository's token (ADR-0006).

## Leak playbook

Follow the steps in this order. Rotating comes first because history rewriting does not un-leak anything:
the secret may already be in forks, clones, CI logs, caches or a scraper.

### 1. Rotate first (within minutes)

| Secret                                         | Rotate at                                                                                               |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| Simulator apps (`fs-dev`, `fs-judge`)          | Nothing to rotate: committed fictional values only the simulator accepts (see above)                    |
| A real PayPal sandbox app (untested)           | developer.paypal.com → Apps & Credentials → the app → generate a new secret, then delete the old one    |
| `FS_COOKIE_SECRET`, `CRON_SECRET`              | Render → fs-api → Environment → new value (for `CRON_SECRET`, the same on fs-cron), then deploy         |
| `FS_LINK_SIGNING_KEY`, `FS_LEDGER_SIGNING_KEY` | Render → fs-api → Environment → a new 64-hex value from the runbook's one-liner, then deploy            |
| `FS_OPERATOR_PASSWORD_SCRYPT`, judge code      | A new hash from `tools/ops-hash-password.mjs` or the judge-code one-liner, set on fs-api, deploy        |
| `FS_APP_DB_PASSWORD`, the owner's URL          | fs_app: a new value on fs-api; the next deploy's migrate resets the role. Owner: fs-db in the Dashboard |
| Anthropic API key                              | console.anthropic.com → API keys → disable and delete the key                                           |
| Gemini API key                                 | Google AI Studio / Cloud console → the key → delete and recreate                                        |
| Render, Expo (`EXPO_TOKEN`), GitHub tokens     | The provider's token settings → revoke                                                                  |
| FCM service account                            | Google Cloud IAM → the service account → delete the key; re-upload via `eas credentials`                |

Then put the new value where it belongs (`.env`, the Render service's environment, the GitHub environment, EAS)
and confirm the service is healthy (`/readyz`). Rotating `FS_COOKIE_SECRET` ends every session, and a new
`FS_LINK_SIGNING_KEY` stops links signed with the old one from verifying. Check the provider's usage logs for calls you did not make.

### 2. Remove it from history with `git filter-repo`

1. Tell every workstream to stop pushing. Note the commit that introduced the secret.
2. In a fresh mirror clone, write the leaked value(s) to a file outside the repo, one per line
   (`<value>==>REDACTED`), and run:

   ```sh
   git filter-repo --replace-text ../leaked.txt
   ```

   To drop a whole file instead: `git filter-repo --invert-paths --path <file>`.
3. Force-push every branch and tag, then ask each worktree owner to re-clone or hard-reset onto the new history.
4. Ask GitHub Support to purge cached views and pull-request refs if the secret appeared in a PR.
5. Delete the `leaked.txt` file.

### 3. Re-run gitleaks

Run gitleaks over the full history and confirm it is clean. A push or PR run of the `gitleaks` workflow does
**not** do this: on those triggers gitleaks-action scans only the pushed or PR commits. Use one of:
- GitHub → Actions → `gitleaks` → **Run workflow** on `main` (workflow_dispatch: the action scans all history
  reachable from `main`), then on each rewritten `ws/*` branch; or wait for the weekly scheduled run (Sundays
  20:43 UTC, `main`).
- Locally, in the rewritten mirror: `gitleaks git --config .github/.gitleaks.toml --log-opts="--all" .` (every
  branch and tag).
  Re-run secretlint (`corepack pnpm secrets:scan`). If the secret showed in a film take or screenshot, re-shoot or
  blur it (risk R17).

### 4. Record it

Add a dated note to `docs/gates/` (or a new ADR if a process changes): what leaked, how long it was exposed, when
it was rotated, and which layer should have caught it.
