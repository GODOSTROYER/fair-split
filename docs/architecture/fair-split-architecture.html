Fair Split · co-op payroll — how it is built and how it works

Every peso, traced to the pencil mark.

Fair Split is payroll for a farmers' co-op whose pay starts on handwritten weigh-slips. A buyer pays one invoice for the season; the co-op splits it across its members, some paid through PayPal and most in cash, all on one statement. Every member can see why her number is her number, and the buyer can re-check every line in its own browser.

  • The model

    Claude reads paper

    Reads each slip photo twice, re-reads doubtful cells, and screens slip text for injected instructions. It never writes a number into a line.

  • Code

    Code computes

    A pure engine computes every line in integer cents from a rate card ratified before the first slip, and holds anything it cannot justify.

  • People

    People approve

    The treasurer resolves holds and signs key 1. The Chair co-signs key 2 for any batch over US$300. Both sign the same batch hash.

  • PayPal

    PayPal executes

    Invoicing v2 bills the buyer, Payouts v1 pays members, signed webhooks confirm. In this build every call goes to a simulated PayPal sandbox.

Runtime

System map

One Node service, fs-api, serves everything from one origin: the API, live event streams, PayPal webhooks, the web console and the mobile app's web build. Postgres holds all state. Slow or irreversible work runs as tasks from a transactional outbox, inside the same process. An hourly cron pings it to reset judge workspaces.

a person's screen pure code, no IO the model simulated, or built but not connected
Execution model

Request path: state and effect commit together

Every command writes its state change, an event row and an outbox row in one Postgres transaction. The effect (a PayPal call, a Claude read, a statement) runs afterwards and is idempotent, so a crash or a retry can never do it twice or lose it. The result comes back the same way, and Postgres NOTIFY pushes it to every open screen over server-sent events.

If the task crashes

The outbox row is still there. A sweeper re-dispatches rows stuck for 5 minutes; tasks load state by id and move it with UPDATE … WHERE state = $expected, so a second run is a no-op.

If the stream drops

The client reconnects with Last-Event-ID and the hub replays the rows it missed. While it is down, the screen polls every 5 seconds.

If PayPal throttles

One limiter in Postgres allows 40 PayPal calls a minute across the service, under the sandbox's 50. A 429 opens a 6-minute circuit. The code never polls.

Pay-run lifecycle

  6. Pay. The simulated sandbox accepts the batch; items confirm one by one. Rhea's item parks UNCLAIMED, so she is paid in cash at the bodega.

AI pipeline · packages/ai

Reading a weigh-slip

Claude turns each slip photo into fields, twice. Code compares the two reads and scores agreement; only a high score is accepted without a person. The model's output schema has no amount field, and slip text re-enters a prompt only as JSON data, so a note in a margin cannot become an instruction.

Scores are fixed constants in packages/domain/src/agreement.ts. Every call goes through ClaudeGateway: a replay cache keyed on sha256 of image, variant, prompt and schema versions, model and effort; per-lane and daily spend caps; a kill_ai_live switch read before every call; any stop other than end_turn goes to a person. Live run R1 (1 Nov 2026) read the 10 hero slips: 10 of 10 exact rows, 0 unsafe auto-accepts, on provisional labels.

Engine · packages/domain/src/engine.ts

Holds: what the engine refuses to guess

The engine computes every line from the ratified rate card (Schedule A, rules R0–R4) in integer cents: premium shared by verified kilos, bonus by verified Grade-1 kilos, largest-remainder rounding with ties to the lower member number. Whatever the rules cannot justify becomes a hold that a person must resolve, by citing a rule or giving a reason. A held line's money is never quietly redistributed.

Invariant I3 · money is conserved

Where the season's money goes

Every cent of Lantern Bay's invoice lands somewhere named. Bands are drawn to scale; the US$3.20 credit is drawn at a minimum width so it stays visible.

Invoice 4,333.50 = pool 4,273.50 + disbursement 60.00 ✓
Pool    4,273.50 = PayPal 341.74 + cash 3,876.43 + kept by co-op 58.53 − credits paid 3.20 ✓
Batch    368.39 = 8 items; Rhea's 26.65 parks UNCLAIMED, returns, and is paid in cash → 341.74 by PayPal ✓

All arithmetic is integer US cents (bigint minor units in Postgres). Peso figures use the run's fixed ₱62.50 per US$, are labelled as estimates, and are never summed. The property test inv.i3.conservation (fast-check) checks the equation on random seasons.

Invariants I4 and I6

Two keys, one hash: the approved digest is the payout

People never approve a screen; they sign a hash. Each line is canonicalised (JCS) and hashed, the batch digest covers every item, and both officers sign that digest with Ed25519. Just before the POST, the Payouts tool ignores everything in memory, re-reads the locked lines from the database and recomputes the digest. If one cent moved, nothing is sent.

Try it in Judge Mode: “Arm a payout change before key 2” moves one payout by one cent after both keys. The Payouts tool re-hashes, sends nothing, and voids both approvals. On a retry that gets “already exists”, the batch is adopted only if every item re-hashes to the approved digest.

PayPal integration · built against the simulator

Invoicing, Payouts and webhooks

Three PayPal APIs carry the money. Invoicing goes through PayPal's own Agent Toolkit 1.11.0; the toolkit has no Payouts tool, so the project owns a typed one in the toolkit's tool shape. Every call in this build hits an in-process simulator that validates requests and responses against PayPal's published specs.

apps/api/src/paypal/webhooks.ts

Payout item status: ranks only go up

Webhooks can arrive late, twice or out of order. Each status has a rank, and an event applies only if it raises the rank. A verified, stored SUCCEEDED applies at once; every other status waits for a fresh GET.

Retry-safe IDs

sender_batch_id is {season}-{rc8}-r{runSeq} and PayPal-Request-Id is its sha256. A re-route of one member gets its own member-scoped id (ADR-0007).

One door to PayPal

All traffic goes through paypal-core's HTTP client with a single-flight OAuth token and the shared limiter. Every call is logged in paypal_calls, which doubles as the limiter's window.

Switching rails

PP_MODE=simulator is the default. PP_MODE=sandbox with a REST app's credentials is designed to point it at PayPal's real sandbox; that path is untested.

Attribution ledger · packages/domain/src/chain.ts, verify-core.ts

Hash-chained ledger and Proof

Every act that matters appends a ledger entry: ratifying the card, accepting a row, raising or resolving a hold, each signature, each payout call, each webhook applied, each kill-switch flip. Each entry's hash covers the previous one. The app role cannot UPDATE or DELETE these rows, and the head is checkpointed with an Ed25519 signature.

Hash values above are illustrative stand-ins; real ones are always computed.

The six plates Proof checks on your device

The Proof page fetches a bundle and the published keys, then runs the same pure verifier the server uses (@fairsplit/domain/verify) with the browser's WebCrypto. A bundle field counts only where a ledger entry attests it, so editing the bundle and re-hashing still fails. pnpm verify-proof <url> runs it from a clone.

plate 1

Paid

The invoice is PAID with 0.00 due, its reference carries the card hash, its total is pool plus disbursement, and an invoice.funded entry attests it.

plate 2

Ratified

The rate card re-hashes to the ratified value, and it was ratified before the first slip, by date and in chain order.

plate 3

Read

Every slip photo's hash is attested by a rows.accepted entry; no photo is listed twice.

plate 4

Computed

Each line re-hashes, cites this card and adds up; the lines sum to the pools; and they were computed before every signature counted.

plate 5

Two keys

Both signatures verify against the published officer keys. Demo keys read “Sample”, never “Verified”.

plate 6

Payout items

Each item is shown at the status its verified notices attest, folded in chain order (ADR-0021).

Architecture §0 · non-negotiable

The eight invariants

Each invariant has a mechanism in code and a property test named after it, so a change that breaks one fails CI by name.

I1

The model never writes a number

Output schemas have no amount fields; the invoice must deep-equal code's quote; statements are templates with placeholders.

inv.i1.no-model-numbers
I2

Rules are frozen before facts

Rate card and GA resolution are canonicalised and hashed; a trigger forbids UPDATE; no slip is accepted before ratification.

inv.i2.rules-before-facts
I3

Money is conserved

Pool = on-rail net + off-rail net + deductions kept + held carried, in integer minor units.

inv.i3.conservation
I4

The approved digest is the payout

Lines are re-hashed from the database immediately before the POST; a mismatch is refused.

inv.i4.digest-is-payout
I5

State only moves forward

Rank-monotonic state machines; UPDATE … WHERE state = $expected.

inv.i5.forward-only
I6

A person approves the irreversible step

The treasurer always; the Chair's Ed25519 co-signature above the threshold.

inv.i6.human-gate
I7

Effects go through the outbox

Every effect is enqueued in the transaction that requires it, and is idempotent.

inv.i7.outbox
I8

Nothing simulated is unlabelled

Every row carries provenance: live, replay, simulated rail or seeded, and the screen shows it.

inv.i8.labels

Invariant I8 · labelled on every screen

What's real, replayed, simulated and synthetic

Real

Your presses, holds you resolve and the Ed25519 signatures you make; every amount the engine computes; the rate card's hash; Proof's checks on your device; R1's committed Claude responses for 10 hero slips.

Replayed

Slip reading in Judge Mode: a labelled seed stand-in, not a Claude recording. Payout steps once the hour's live quota is spent, labelled as a replay.

Simulated

Every PayPal call, ID, status, webhook and fee. Simulator IDs carry SIM (e.g. INV2-SIMx-…) and debug IDs start sim-. Also push banners and the biometric step.

Seeded

The invoice-send approval, and the manifest entries for 54 earlier photos with their read dates.

Synthetic

The co-op, its 64 members and officers, Lantern Bay, 264 slips, the rate card, the logbook and every voice.

Not built yet

Hosted demo, APK, push, offline clerk capture, real SMS, iOS, the audit agent, and production partner onboarding.
